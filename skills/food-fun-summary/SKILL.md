# 吃喝玩乐汇总

把用户刷到的餐厅、咖啡、景点、玩乐地点持续积累为可查找的本地指南库。触发后直接处理已有材料；用户只说“吃喝玩乐”却没有材料时，简短请其发送链接或截图，不凭空选题。

## 固定位置与合同

- GitHub：`xinna2001/food-fun-summary`，中文标题「吃喝玩乐汇总」。默认保持当前可见性。
- 本机：`/Users/bytedance/food-fun-summary`。迁移主机时先从 GitHub 克隆到可写目录，再以实际目录传 `--repo`。
- 本 Skill 随该仓库版本管理，并以本地目录加载到希儿；不自动复制到其他共享 Skill 库。
- 后续收录、更新和本 Skill 修改默认通过独立分支创建 Pull Request（PR），便于记录贡献与提交量；不直接推送主分支。用户已授权：本仓库由本人 `xinna2001` 创建的 PR，必要检查通过后直接合并，不等待人工审核或再次确认。
- `README.md` 首页固定三列：`地点/店铺`、`详细信息`、`原始链接`。同时生成相同三列的 `吃喝玩乐汇总.csv`。
- 每个地点一篇 `topics/<id>/README.md`；索引中第二列链接到该文件。一家店/景点对应一条；一个视频含多个独立地点时可拆为多行，共用原始链接并人工标明关联。
- 以用户输入顺序追加。同一地点复用 id、更新原条目并合并原始链接；不要重新排序或覆盖旧来源。
- 只有截图时第三列写“截图提供，原链接待补”；找不到链接不能编造。

## 执行流程

### 1. 恢复仓库与输入

先执行 `gh api user --jq .login`、`git -C /absolute/repo status --short` 和 `git remote -v`，核对身份与目标。已登录张加恩的 GitHub 身份在本仓库维护任务中可以继续使用；其他用户要求修改此私人仓库时必须有仓库所有者授权，不将主机登录态视为任何人都能写入的许可。

确认默认分支（当前为 `main`），工作区干净时先 `git fetch origin`，从最新 `origin/main` 创建本轮独立分支。若已在本轮 PR 分支，核对其目标分支和现有 PR 后继续使用；不要重复开分支或 PR。已有未提交修改时保留它们，用独立分支/工作树完成当前条目，避免混入他人改动。身份不匹配或无权限时先完成可做的本地研究并报告准确阻塞。

读取 `data/topics.json` 查同名地点、抖音视频 ID 和原始链接。记录本轮所有输入，按用户顺序处理；同一地点上一轮已进入本流程时，继续接收后续链接和截图。

### 2. 读取素材并溯源

按 [sources.md](references/sources.md) 选择路径。优先读抖音视频标题、字幕、定位与评论；不能仅凭达人一句“超好逛”断言准确地址与人均。提取店铺/景点名称、城市、商圈、招牌或玩法关键词后，到大众点评、美团、地图检索一手信息。记录实际查阅日期，把关键数字（人均、评分、门票）区分成“已核实 / 达人宣称 / 推测”。资料无法获取时，继续调查可用的一手来源，同时说明原素材实际读取范围。

### 3. 写详细地点页

复制 [place-template.md](assets/place-template.md) 到 `.work/<id>/report.md` 并完整填写。核心内容是：这是什么店/景点、确切位置与交通、人均消费、评分与真实评价、值得去还是踩雷。引用使用可点击的真实 URL 和 `[S1]` 编号。

人均、评分、门票必须标注查阅日期，因为会随活动变动。受登录或验证码限制而读不到点评页时，如实写“当前未发现，后续随新资料更新”，不为了凑报告伪造价格或评价。没有实地去过时，“实际去过后补充”一节留空，不编造体验。

### 4. 写入三列索引

使用 Python 3 标准库脚本 `scripts/catalog.py`。下文 `SKILL_ROOT` 为本 Skill 所在目录、`REPO` 为实际仓库位置。新建条目 JSON，例如：

```json
{
  "id": "2026-11-04-example-restaurant",
  "name": "真实店名或景点名",
  "sources": [
    {"kind": "douyin", "url": "https://真实抖音地址", "title": "原视频标题", "note": ""}
  ]
}
```

`kind` 可选 `douyin`、`bilibili`、`youtube`、`wechat`、`web`、`screenshot`、`dianping`、`meituan`。仅截图来源可以不带 URL，此时 `note` 必填。

```bash
python3 "$SKILL_ROOT/scripts/catalog.py" --repo "$REPO" upsert \
  --entry "$REPO/.work/item/entry.json" --report "$REPO/.work/item/report.md"
python3 "$SKILL_ROOT/scripts/catalog.py" --repo "$REPO" check
```

使用相同 `id` 更新既有地点；保留旧报告仍然有效的内容和更新记录。脚本合并来源、保留行序，并拒绝将同一来源误记到另一个 id；一个视频确实含多个独立地点时，经阅读确认后加 `--allow-shared-source`。不同链接的同一地点依靠语义识别合并，脚本不会自动替代此判断。

首次初始化空仓库可用 `init`；由数据重新生成索引可用 `render`；`list` 可查看当前条目。不要手工修改自动索引块。

### 5. 通过 PR 提交和回读

检查 `git diff`，确认来源、中文、文件路径和三列顺序正确。对本轮新增/更新的地点页检查每项关键数字（人均、评分）都有实际读取到的证据；确认未把凭据、临时大媒体或测试条目纳入提交。

只 `git add` 本轮具体的报告、`data/topics.json`、`README.md`、`吃喝玩乐汇总.csv` 及必要的局部证据文件；修改本 Skill 时只额外加入实际变更的 Skill/维护规则文件。提交后正常推送本轮分支，并创建以 `main` 为目标的 PR；已有同一任务 PR 时更新原 PR。用户已明确授权地点收录、PR 提交及本人在本仓库的 PR 检查通过后直接合并，不用逐条再确认或等待人工审核。

```bash
git push -u origin <本轮分支>
gh pr create --repo xinna2001/food-fun-summary --base main --head <本轮分支> \
  --title '<具体变更>' --body-file '<UTF-8 PR说明文件>'
# 完成下述检查并核对最新 head SHA 后合并
gh pr merge <PR号> --repo xinna2001/food-fun-summary --merge \
  --match-head-commit <已核对的head-SHA>
```

PR 说明概括具体收录/更新内容、来源与验证结果，保留未实测状态。提交前再次 `fetch` 核对主分支；远端领先则整合最新改动。catalog 冲突保留双方来源和顺序，再 `render`、`check`，禁止盲目用 ours/theirs 覆盖整份 JSON；无法判断的同一报告语义冲突才询问用户。禁止强推。

推送报错或超时时先查远端分支 commit；创建 PR 结果不确定时先按 head/base 查询已有 PR，避免重复提交。比较 `git rev-parse HEAD` 和 `git ls-remote origin refs/heads/<branch>`，用带 `?ref=<branch>` 的 GitHub Contents API 回读本轮文件，并核对 PR 的 URL、作者、head/base 和 head SHA。

合并前确认 PR 作者为 `xinna2001`、base 为 `main`、head SHA 与本轮推送一致，目录/Skill 等必要本地检查通过，GitHub 必需检查通过且没有合并冲突；然后使用正常合并接口直接合并。检查失败或冲突先修复并重验，不能把检查结果或审核状态伪写成通过；此授权只适用于本仓库的本人 PR，不扩展到第三方仓库。

合并后核对 PR 的 `MERGED` 状态与 merge commit，回读主分支上的本轮文件，再将干净的本地工作区切回 `main` 并 `pull --ff-only`。主分支回读一致后报告“PR 已合并，主分支已同步”。检查尚未完成或合并尚未成功时分别说明实际状态与原因，不把正常流程停在等待人工审核。提交成功但未推送成功时说明“本地已保存，GitHub 尚未同步”；分支已推送但 PR 未创建成功时分别说明两个状态。

### 6. 当前话题交付

回复收录/更新数量、简要结论（店名、人均、值不值得去）、PR 链接、合并后的地点页链接、合并状态和实际缺口；尚未合并时链接到 PR 分支并说明原因。飞书会话用 `botmux send --response-kind final --mention-back` 在当前话题发送一次最终结果，复杂发送前读 `botmux-send`。不额外向其他人发消息。

- 同一地点更新而不重复，原始链接不丢失；截图缺链有明确状态。

- 本人 PR 必要检查通过后直接合并；`MERGED` 状态、merge commit 和主分支文件回读核对正确。
